# 考慮漏れの修正の指示

Claude のスケジュールタスク（毎時）が、この文書に従って、テストガチャで見つかった考慮漏れを修正する。
作ったプルリクエストは人がマージする。**自分ではマージしない。**

## 1. やること

1. 作業するブランチを決める
    - `fix-` で始まるブランチの、マージされていないプルリクエストがあれば、そのブランチを取り出して `origin/main` をマージし、その続きに作業する（プルリクエストは 1 つにまとめる）
    - なければ、`main` から `fix-YYYY-MM-DD-hh`（日本時間。`TZ=Asia/Tokyo date +%Y-%m-%d-%H`）を作る
2. すべてのテストデータでテストガチャを実行し、結果を確認する

    ```bash
    uv sync --locked
    uv run python tools/run_all_gacha.py --verbose --json "$TMPDIR/before.json"; echo "終了コード: $?"
    ```

    | 終了コード | 意味 | 次にすること |
    |---|---|---|
    | 0 | 失敗したテストデータがない | 何も変更せずに終わる（プルリクエストも作らない） |
    | 1 | 失敗したテストデータがある | 3 に進む |
    | 2 | テストを実行できなかったファイルがある（出力に「実行できなかった」と出る） | 7 章に従う。**「失敗がない」と扱わない** |

    終了コードと「合計」の行の両方を見る。出力を最後まで読まずに判断しない
3. 失敗したテストデータを 1 件ずつ確認する。`--verbose` の出力から、次のことを読み取る
    - どちらの対象で失敗したか（`text_to_page_grouper`・`page_to_slideir_page`）、何ページ目か
    - 期待値と実際の値の差分（`-` の行が期待値、`+` の行が実際の値）
    - 例外が出ている場合は、その種類とメッセージ
    - テストデータの `input_text` と期待値（`tests/test_data/` の該当のファイルを開いて読む）

    差分を読まずに、`test_data_id` や観点の名前だけから原因を推測しない
4. 確認した内容をもとに、2 章に従って「考慮漏れ」か「期待値の誤り」かに分ける。同じ原因の失敗はまとめる
5. 考慮漏れは 3 章に従って `target.py` を直す。期待値の誤りは 4 章に従って除外する
6. 5 章の確認をする
7. コミットして push し、プルリクエストを作る（すでにあれば本文を更新する）
    - タイトル: `考慮漏れの修正 YYYY-MM-DD-hh`
    - 本文: 6 章

## 2. 考慮漏れか、期待値の誤りか

根拠にするのは、[plans/2026-11-20-first-implementation.md](./plans/2026-11-20-first-implementation.md) の 2 章、[slide-ir.md](./slide-ir.md)、[test-data-generation.md](./test-data-generation.md) の 5 章。

| 判断 | 条件 | 対応 |
|---|---|---|
| 考慮漏れ | 期待値が仕様のとおりである。または、仕様にない書き方で、期待値が「作業メモを書いた人が意図したスライド」として自然である | `target.py` を直す |
| 期待値の誤り | 期待値が仕様と食い違う。`input_text` にない文字が期待値にある。ほかのテストデータの期待値と両立しない | 除外する |
| 判断できない | どちらとも言える | 直さず、除外もせず、プルリクエストの本文に書く |

期待値に合わせるために仕様を曲げない。迷ったら「判断できない」にする。

## 3. 修正の仕方

- 変更してよいファイルは次の 3 つだけ

    | ファイル | 変更 |
    |---|---|
    | `target.py` | 考慮漏れの修正 |
    | `tests/regression_data.json` | 修正したテストデータを写す |
    | `tests/excluded_test_data.json` | 期待値の誤りの除外 |

- テストデータ（`tests/test_data/`）、テストの仕組み（`tests/*.py`・`tools/`）、ワークフロー、文書は変更しない。直す必要があると考えたら、プルリクエストの本文に書く
- **入力ごとの場合分けで通さない。** `test_data_id` や特定の文字列を見て結果を返すような修正はしない。同じ種類の書き方すべてに効く規則として直す
- 1 つの原因で失敗しているテストデータは、まとめて 1 つの修正にする
- 修正したら、その原因を代表するテストデータを `tests/regression_data.json` に写す（そのままの形で追記。1 つの原因につき 1〜2 件）
- 標準ライブラリだけを使う。XML は文字列の連結ではなく `xml.etree.ElementTree` で組み立てる

## 4. 期待値の誤りの除外

`tests/excluded_test_data.json` に追記する。除外したテストデータは、テストガチャで実行されなくなる。

```json
[
  { "test_data_id": "2026112110-07", "reason": "期待値の <Str> に、input_text にない文字がある" }
]
```

理由は、人が読んで確かめられるように具体的に書く。

## 5. 確認

```bash
uv run pytest --ignore=tests/test_gacha.py     # 仕組みのテストと再発のテスト
uv run python tools/run_all_gacha.py --verbose --json "$TMPDIR/after.json"; echo "終了コード: $?"
```

それぞれの出力を読んで、次のことを確かめる。

- `pytest` が、失敗もエラーもなく終わっている（最後の行が `N passed`）。`failed` や `error` があれば、その内容を読んで直す
- `run_all_gacha.py` の終了コードが 0 か 1 である（2 なら、修正でテストを実行できなくしている）
- 失敗の件数が、修正の前（`before.json`）より減っている
- 修正の前に通っていたテストデータが、修正の後に失敗していない（`before.json` と `after.json` を `test_data_id` と対象ごとに比べる）
- まだ失敗しているテストデータは、差分を読んで、直しきれていないのか、別の原因なのかを確かめる
- `git status` で、変更が 3 章の 3 つのファイルだけである

通らないときは、通るまで直す。直せない修正は取り消して、プルリクエストの本文に書く。

## 6. プルリクエストの本文

人がマージするかどうかを判断する材料を書く。

```markdown
## 結果

| | 修正の前 | 修正の後 |
|---|---|---|
| 失敗したテストデータ | 12 / 30 件 | 3 / 30 件 |

## 修正した考慮漏れ

| 原因 | 対応 | テストデータ |
|---|---|---|
| 表紙（`# `）を扱っていない | `# ` の行を 1 ページにし、CoverPage に変換する | seed-0003、2026112110-01 |

## 期待値の誤りとして除外したもの

| test_data_id | 理由 |
|---|---|

## 判断できなかったもの・直せなかったもの

| test_data_id | 内容 |
|---|---|

## 仕様に足したほうがよいこと

仕様にない書き方について、今回どう扱うことにしたか。
```

## 7. テストを実行できなかったとき

`run_all_gacha.py` の終了コードが 2 のとき、または `pytest` がテストを集める段階でエラーになったときは、エラーの内容を読んで原因を分ける。

| 原因 | 対応 |
|---|---|
| `target.py` が読み込めない（構文エラー、import の失敗など） | `target.py` を直す。考慮漏れの修正と同じプルリクエストに含める |
| テストデータのファイルが壊れている（JSON として読めない、項目が足りないなど） | テストデータは変更しない。そのファイルを除いた残りで作業を続け、プルリクエストの本文の「判断できなかったもの・直せなかったもの」にファイル名とエラーを書く |
| テストの仕組みや環境の問題（`uv sync` の失敗、仕組みのテストの失敗など） | 何も変更せずに終わり、エラーの内容を通知する |

原因がわからないまま、「失敗がない」として終わらない。
