## 背景: ルビ振りを自動化するモジュール
仕事で、文章にルビ（ふりがな）を振るモジュールを作りました

## 考慮漏れがたくさん見つかった
- テストは書いていた
- それでも、使ってみると想定していない入力が次々に出てくる
- テストケースは、自分が思いつく範囲でしか書けない

## 直すと、別のところが崩れる
修正の方針を考えるたびに、こうなりました
1. A の入力に対応する
2. すると B の入力の結果が変わる
3. B を直すと、今度は C が崩れる

> これを修正すると、これが崩れる

## 足りなかったもの
- 自分では思いつかない入力
- 直したものが、あとで崩れていないことの確認

## そこで TGDD

## TGDD とは
**テストガチャ駆動開発**のことです
- 毎日ちがうテストケースで検証する
- 考慮漏れを見つける
- 対応策を考える
- コードを修正する

プロダクトの開発とは切り分けて、モジュールの単位で回します

## なぜ「ガチャ」なのか
- ふだんのテストは、*通ると思って*実行する
- テストガチャは、通るかどうかわからない
- 考慮漏れと出会えるかどうかは、偶然

## TGDD のサイクル
1. AI がテストデータをつくる
2. テストを実行する
3. 失敗したら、考慮漏れかどうかを確かめる
4. コードを直す
5. 同じ考慮漏れが再発しないように、テストを残す

## 今回の題材
作業メモからスライドをつくるプログラムです
- `text_to_page_grouper()`
  - 作業メモを、ページごとに分ける
- `page_to_slideir_page()`
  - 1 ページ分のテキストを、スライドのデータ（XML）に変換する

このスライドも、この 2 つの関数を通っています

## 用意したもの

| やること | 担当 | 頻度 |
|---|---|---|
| テストデータをつくる | Claude のスケジュールタスク | 毎時 |
| テストデータを検査してマージする | GitHub Actions | プルリクエストごと |
| 考慮漏れを直す | Claude のスケジュールタスク | 毎時 |
| 修正をマージする | 人 | 気づいたとき |

## テストデータの形
入力と、期待する結果の組です

```json
{
  "test_data_id": "2026112110-01",
  "input_text": "## 見出し\n- 箇条書き",
  "expected_page_group": ["## 見出し\n- 箇条書き"],
  "expected_slideir_page": ["<GeneralPage id=\"p1\">...</GeneralPage>"]
}
```

## テストは 2 種類
- **テストガチャ**（`test_gacha.py`）
  - 考慮漏れを見つけるためのテスト
  - 失敗するのが正常
- **再発のテスト**（`test_regression.py`）
  - 直した考慮漏れが、また崩れていないかを確かめるテスト
  - 失敗してはいけない

## 苦労したこと
- AI がつくる期待値が、正しいとは限らない
  - 失敗が「考慮漏れ」なのか「期待値の誤り」なのかを見分ける必要がある
- 仕様にない書き方の正解を、だれかが決めないといけない
- テストの仕組みだけは、正しく動かないといけない

## 良かったこと
- 自分では思いつかない入力が来る
  - 全角の `＃＃`、CRLF の改行、`*` と `-` が混ざった箇条書き
- 直すたびに、再発のテストがたまっていく
- 「これを直すと、これが崩れる」に、すぐ気づける

## 人がやること
1. 期待値がおかしくないかを見る
2. 仕様にない書き方の扱いを決める
3. 修正のプルリクエストをマージする

考えることは減らないけれど、~~思いつく~~**見つける**のは任せられる

## まとめ
- テストケースを自分で考える限り、考慮漏れは自分の想像の中でしか見つからない
- テストガチャは、想像の外から入力を持ってくる
- 見つけた考慮漏れは、再発のテストとして残す
- 完璧なプログラムではなく、**良くなり続ける仕組み**をつくる
